## Introduction

Orchestration Architect the project will use `literate documents` so that 
the project can be re-generated from specifications, and to ensure coherence 
and an easy way to test the tools as they are being specified from within the 
document itself.

The goal is the have `literate specifications` that are able to
 generate the implementation of the subject matter. 

The idea behind `literate documents` is that the *document* contains a one line 
command, that can be executed by tooling, or invoked by the reader, to bootstrap
the self-assembly of the document.

The supplied command should `tail` a document from the last heading
(enriched using the tools generated by the `SPEC-000 Literate Specification`).

The functionality provided should *identify* macros and regions,
defined by `CONCEPT-001 Abstract Compositional Topology`.
and then a *literate implementation* heading should contain a block composed of 
concatenated macro tokens. The resolution of these tokens should generate the
subject of the document.

## Scope of the Design 

### Problem Statement

The challenge of keeping documentation update to date with changing
specifications due to the architectural decision to embrace chaos and to
facilitate a repeatable transisent structure.

The need to reduce dependence on third-party dependencies has lead to
difficulties keep track of the monitoring of different components and systems.
  
Furthermore, the development team size of one (myself), and intricate concepts,
have lead to challenges with *cognitive overload*.
   
Though work has been made on designing the project managmeent system naturally
cohere,  with the natural transclusion (tasks split by project, naturally hide
the tasks not being worked on), and the preorders that arise from the manner in
which things are worked on, keeping a temporal structure allowing for cognitive
mapping to what it important,  and the ability to capture potential resources,
should the need come.
  
However, the benefits of this is under utilised due to the complex domain logic,
which represents naturality, and it is best explained as a document.
  
Futhermore, the notes system has shown that more documents is not the answer,
it is quality that counts, which `literate documents` facilitates builtin
self-acutalisation of potential resources.

### Goals and Objectives

Since the system has been designed to be able to assemble itself from
specifications, it just makes sense to embrace Knuth's literate writing 
concepts.

As work has already been done in making a set of primitives that is able to
compose operations, and match regions it will allow for these category theoretic
concepts to demonstrate its generality.

The challenges that need to be addressed:

- A consistent description of the types of documents;

- Markers that can identify tokens from the implicit structure,
    such its specifications facilitations simple extension

- A consistent URI schema and resolution 

- Configurations have a standard location,
  that is decoupled from the environment

- The need for the shell configurations (zsh, bash and fish) to be configured
    uniformly such that:

    - Required *OA Environment Paths* can be added.

    - Environment Variables are available 
    
- The system needs to be able to generate the necessary components across
  various environments 

The system is designed to be composable, as the project is a solution generator, 
  not merely the solution, so the the needed parts need to be added 
  within the composable component.

There is a need to be able to specify tools and have them available to the
 systems $PATH, and that environment variables for different apis need
 to be made avaiable when used.

Further efforts to automate the generation of diagrams (`d2` in particular),
needs to be able to map the structure of the project, based on experiments.

In addition to needed to describe a DSL for yaml and markdown,
such that the operational primitives selected to achieve correctness,
is able to be reused from a core abstract specification of the operations. 

## Analysis

Experiments have demonstrated the ability to introduce major changes,
  in which a prototype with a rust web application, 
  to compare the feel of working with a different dependency, 
  a manifest was created which generated a literate document,
  was tangled together, then by rewriting the parts in the document,
  it was able to generate both variants. 

This will also be useful to apply sunset protocols when migrating systems.

Further experimental work, where the developer was exploring how to use components,
  the ability to describe what is being examined, and getting each part to work, 
  while learning, ensures that the rationale is 
  not lost due to large amounts of information.

Furthermore, having literate documentation provides LLM more context 
when looking at an implementation, in fact, the goal is to be able to use
literate writing, to describe AI functions and tools,
such that a literate document can be used to iterate amongst different agents,
that have different goals, such that the AI agents can achieve retrospective
self-reflection, and apply the concepts from Minksky (2008).

The idea is that changes in the thought processes need to occur at the layer 
at which the problem pertains, such that the underlying structures
naturally transform.

The swapping out of a higher level order structure should be made much easier 
  with each component semantically linked via a web of documents, and the 
  compositionality required for literate writing should facilitate migrations 
  as it provides a literal literate blueprint that needs to be updated. 

Furthermore, the use of literate documents achieves the goal of turning certain
aspects of the system to become more instinctual and provides a form of resource
development.

As more resources are needed, the process of generating the necessary resources
to complete a task, will become a core competency, with the compositional 
naturality lending itself to achieve a dynamic capability.

### Challenges 

The challenges with literate writing is a skill issue.

Fortunately, the nature of doing literate writing, with self-assembly,
ensures that a step backwards, is that all changes must occur
through the writing.

Thus, it provides a clear way to analyse what is going wrong through the use of diffs
that show in natural language the problem.

This may make development take longer, this may reduce agility in the short 
term, but agility has been the problem of late.

Furthermore, this will provide a wide range of data for fine tuning LLMs,
though ideally LLMs will be required, by should be able to assist by requiring
careful consideration. 

A recent challenge has been context switching between different architectural
perspectives. 

However, this `DESIGN-001 Literate Documents` has covered a lot of the 
high level challenges, and will this allow for coherence between documents,
as it provides a framework which provides natural language explanation of the
thought process that led to the current state of development. 

### Possible Solutions 

✖ **Use a database**

  That goes against the principles of having minimal dependencies,
    and a specification based, human readable and transparent system,
    that is able to regenerate itself.

  The system has requirements of being able to generate systems in air-gapped
    environments, and needs to reduce the risk of supply chain attacks.
    
  Furthermore, databases are not composable,
    and are not the direction to find the emergent effects.

  The system can use databases, but not as its core,
    it must be able to generate the environment and the database; but using a
    database (at this point), would detract from the goal of discovering the
    ideal and universal solution.
    
  Furthermore, can you imagine Knuth using a database to build TeX, the modern
   developer would try, however the structures that seem most promising,
   and a path to strategic capabilities (such that they are not emulatable by
   humans or AI, is slowly working through and implementing the 
   components needed as they arise). 

✖ **Use AI**
    
  AI cannot at this stage, be useful until the architectural framework 
    clearly defines the boundary of the context. Furthermore, this will
    generate more problems than it will solve.

  The ideas being explored are deep ideas, that AI struggles with, 
    such that it is more of a burden to provide it with context than it is worth.
    
  Furthermore, the work is based on readings and research, that to provide to the AI 
    would be a waste of time, if I could just implement it literately, thereby killing 
    two birds with one hatchet.

✖ **Give up on the project**

I wish this was the correct answer, but there is much to discover, this journey continues...

✔ **Use Literate Writing**

This works, because as ideas from people much smarter than us are explored,
  the literate writing works 3-fold: it forms the study notes, which are put into practice,
  which describes the implementation, which is the implementation.
  
  The goal is the achieve the last step, such that the literate documents have a structure,
  that it can use the web of ideas, to bootstrap itself. These will include macro resolution,
  ensuring designs are composable, and even embedding tooling in the document itself,
  such as vim plugins, the ability to generate bash tools,
  and link different systems in a natural way.

### Implementation Strategy

The `LIT_SPEC` project will provide `SPEC-002 Configuration Specifications`, 
as the first literate.

Such that following objectives will be prioritised:

**Configuration Specification** Setting up the environment variables
from a bootstrapped specification.

**Document Semantic and Structure Specifications**  The *specification* needs 
to be minimal but extensible. The literate document capabilities, are a mainly 
an effort of diving through the projects history and backups. 
Each *document class* need to achieve an *outcome*.

**Environment Setup** The configuration management should be able to bootstrap
 the environment, and other environments,  will need to be put on the backlog. 
 This includes setting up system wide (in `/usr`, `/bin`, `/etc` and `/var`) 
 and the **XDG** compliant user specific paths.
 
**Multi-Shell Support**: The system should be able to provide configurations 
that work with `fish`, `zsh`, `bash` and `sh`.
 
**Tooling Integration**: Though after bootstrapping 
the configuration specification, the most useful capabilities will be to
integrate the `shell` and `neovim` to the project via the specifications.

These will be used to create the minimal `SPEC-000 Literate Specification`
that can bootstrap `SPEC-001 Configuration Specification`
which will generate the configurations needed to 
setup the environment variables. As there exists a solution that
works with `bash` and `fish`, other shells will be added as needed.
This will be done at the adjunction of the sheafs.

The system will use `XDG Standards` by default, and if not available, will use the default locations for placement of user space configurations. However, these will be described by the Literate `SPEC-002 Configuration Specification`.
